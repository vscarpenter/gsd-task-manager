The big picture

Where data lives

Source of truth is local IndexedDB. PocketBase is a mirror for multi-device fan-out, not the database of record. Once a task has synced, a newer remote edit or a remote deletion still applies locally.

What triggers a sync

A task edit queues an op and schedules a debounced sync. A start-up sync, the periodic timer, a return to the tab, coming back online, and the sync button also reach coordinator.requestSync().

Conflict resolution

Last-write-wins on client_updated_at. A strictly newer timestamp wins. On a tie the local copy stays.

Realtime

SSE subscription delivers other devices' writes immediately. Periodic sync is a safety net.

Auth flow

The app runs the OAuth manual code flow. The user clicks a provider button and a popup opens the provider page. PocketBase bounces the result to the app's /auth/callback/ page, which relays the code to the tab that started sign-in. That tab exchanges it with authWithOAuth2Code, and the SDK stores the token in localStorage. The app refreshes the token itself: ensureValidAuth runs at the start of each fullSync. Never call the realtime authWithOAuth2({ provider }) form. It delivers the code to whichever realtime client the request's state value names, so a crafted link can hand a victim's code to an attacker.

lib/sync/pb-auth.ts:loginWithProvider 
// Runtime allowlist — type erasure means callers could pass anything
const ALLOWED_OAUTH_PROVIDERS = new Set<OAuthProvider>(['google', 'github', 'apple']);

// Simplified. The real function also handles cancel, timeout, and closing the popup.
export async function loginWithProvider(provider: OAuthProvider, options = {}): Promise<AuthState> {
  if (!provider || !ALLOWED_OAUTH_PROVIDERS.has(provider)) {
    throw new Error(`OAuth provider not allowed: ${String(provider)}`);
  }

  // runCodeFlow: listAuthMethods, open the provider page, wait for the relayed
  // code for this tab's state, then authWithOAuth2Code with the PKCE verifier
  const authData = await runCodeFlow(provider, options, signal);

  return {
    isLoggedIn: true,
    userId: authData.record.id,   // becomes the `owner` FK on every task row
    email: authData.record.email,
    provider,
  };
}

Why the allowlist isn't theatre

Without it, loginWithProvider would start sign-in for any provider string a caller passes, if the server has that provider configured. It accepts only the three the app has sign-in buttons for.

03

Local mutation → push

A task edit writes to Dexie and, when sync is on, enqueues a sync op in the same transaction. The queue is durable (it's an IndexedDB table), so offline edits survive a reload and get flushed on the next successful sync.

lib/sync/pb-push.ts:pushLocalChanges 
// Simplified. Counters and the result object are left out.
export async function pushLocalChanges(sessionOwnerId: string): Promise<PushResult> {
  const ownerId = resolvePushPrincipal(sessionOwnerId);   // throws if the SDK user is not the session owner
  if (!ownerId) return { ..., authenticated: false };  // no-op when logged out

  const pending = await readPendingForSession(ownerId);   // session check, then the pending rows
  if (pending.length === 0) return { ..., authenticated: true };

  for (const item of pending) {
    try {
      // Looks up this row's remote record, then creates, updates, or deletes it.
      // Skips and dequeues a stale op when the remote is strictly newer (a far-future stamp never counts).
      const outcome = await pushSingleItem(item, ctx);   // 'pushed', 'skipped', or a failed lookup
    } catch (error) {
      if (isSessionCheckFailure(error)) throw error;   // session ended: stop, count no retry against any row
      lastError = await recordItemFailure(item, error, ownerId);   // stable code only — raw 4xx bodies can echo task text
      if (isRateLimitError(error)) break;            // 429 → abort, don't amplify the storm
    }
    await delay(THROTTLE_MS);   // 100ms gap between items, skipped after the last one
  }
}

Failed items aren't deleted

After SYNC_CONFIG.MAX_RETRIES attempts, a queue item flips to status: 'failed' and stays in db.syncQueue. The health check reports them as a failed_items issue. getPending() filters them out so they don't clog the push loop, and nothing re-arms a failed row.

04

Pull & last-write-wins

Pull uses a cursor (lastClientUpdatedAt) so we only fetch what changed since last time. The filter is the most subtle part. The first gotcha explains why we can't use PocketBase's own updated column. An ordinary sync pushes, then pulls. A backfill sync is the exception (ADR 0020). It runs when the stored pull contract version is missing or older than this build's, until a pull completes. That sync pulls before it pushes, ignores the cursor, and accepts tied records. After both passes, resurrectOnSight brings back a remembered task whose Trash delete never reached the server, if the account still lists it.

lib/sync/pb-pull.ts:pullRemoteChanges 
// Simplified. The return value is left out.
export async function pullRemoteChanges(lastClientUpdatedAt: string | null, options = {}) {
  const ownerId = getCurrentUserId();
  if (!ownerId) return { ..., authenticated: false };

  assertSafeRecordId(ownerId, 'ownerId');           // reject filter-injection attempts

  let filter = `owner = "${escapeFilterValue(ownerId)}"`;
  if (lastClientUpdatedAt) {
    filter += ` && client_updated_at >= "${escapeFilterValue(lastClientUpdatedAt)}"`;
  }

  const records = await fetchBoundedRemoteTasks({   // paged, throws past SYNC_CONFIG.MAX_REMOTE_TASKS
    filter,
    sort: 'client_updated_at,task_id,id',   // NOT `updated` — system fields aren't sortable in PB v0.23+
  });

  // One Dexie transaction: session check, archive and Trash tombstones, then LWW.
  // A strictly newer remote wins. A tie keeps the local copy, except during a backfill.
  const { appliedRecords } = await applyRemoteRecords(records, ownerId, options);

  // The next cursor comes only from applied records, minus a 30-second overlap.

  await reconcileDeletedTasks(ownerId);   // drop local rows the server no longer has
}

The mapper layer is the single place where camelCase ↔ snake_case lives, and it also keeps device-local fields (reminder state and snooze) from the local row, so a sync doesn't undo “I dismissed that ping on this device”. A pull that moves the due date resets them:

lib/sync/task-mapper.ts:pocketBaseToTaskRecord 
export function pocketBaseToTaskRecord(record, existingLocal) {
  const parsed = pbTaskRecordSchema.safeParse(record);   // fail closed on malformed remote payloads
  if (!parsed.success) return null;

  const r = parsed.data;
  return {
    id: r.task_id, title: r.title, /* … */
    // notificationSent, lastNotificationAt, snoozedUntil: per-device, reset when the due date moves
    ...localReminderState(existingLocal, r.due_date || undefined),
    parentTaskId: existingLocal?.parentTaskId,   // no wire field, always from the local row
  };
}
05

Realtime (SSE)

The periodic sync covers correctness; the SSE subscription covers latency. The subscription delivers writes on the tasks collection, whose rules require owner = @request.auth.id. The handler also drops any event whose owner is not the current user. We filter out our own writes by device_id so we don't ping-pong our changes back into Dexie.

lib/sync/pb-realtime.ts:handleRealtimeEvent 
// Simplified. The real subscribe is single-flight per device and drops a replaced subscription.
export async function subscribe(deviceId: string) {
  currentDeviceId = deviceId;
  unsubscribeFn = await pb.collection('tasks').subscribe('*', handleRealtimeEvent);
}

async function handleRealtimeEvent(event) {
  // task-mapper.ts validates task_id, owner, and device_id
  const record = getPocketBaseRealtimeEnvelope(event.record);
  if (!record) return;   // fail closed on weird shapes from a compromised server

  // Echo filter — require BOTH non-empty so cold-start (null deviceId) doesn't swallow everything
  if (record.deviceId && currentDeviceId && record.deviceId === currentDeviceId) return;
  const userId = getCurrentUserId();
  if (record.ownerId !== userId) return;

  await applyRemoteChange(event.action, event.record, userId);   // strictly newer remote wins, as in pull
}
06

The coordinator

Two callers reach requestSync(): the sync button, and the background sync manager for its start-up, timer, tab-visible, back-online, and after-change triggers. The coordinator collapses concurrent requests into one in-flight sync plus at most one queued follow-up, with user-priority overriding auto-priority.

SignalWhereWhat happens
Click “Sync now” sync-provider.tsx requestSync('user') — bypasses backoff
Start-up, timer, tab visible, back online background-sync.ts requestSync('auto') — gated by retry backoff
Local mutation tasks/crud/helpers.ts Enqueue, then a debounced requestSync('auto') when background sync is running
SSE event pb-realtime.ts Apply directly via applyRemoteChange()
Health monitor health-monitor.ts Reports issues, never requests a sync itself
07

Gotchas

System fields are unsortable / unfilterable in PocketBase v0.23+

You cannot sort: '-updated' or filter: 'updated > X' — the query parser refuses. Every timestamp the sync code filters or sorts on is client_updated_at, a custom field set from task.updatedAt. Same applies to indexes: custom indexes can't reference updated/created.

Admin endpoint moved

Use /api/collections/_superusers/auth-with-password, not the legacy /api/admins/auth-with-password. If you script collection setup, hit the new one.

_pb_users_auth_ is not a real collectionId

Don't use that placeholder as the collectionId of a relation field — it silently breaks. Either use a plain text field for the owner FK (what we do), or look up the actual users-collection id and substitute it.

SDK auto-cancellation stays off

With auto-cancellation on, the SDK can cancel one in-flight request when another starts. Push, pull, and other callers overlap, so the singleton calls autoCancellation(false). Don't re-enable it.

100ms throttle is load-bearing, not paranoia

PocketBase returns 429s under bursts. We sleep THROTTLE_MS between push items, and if a write still returns a 429 we abort the push loop early rather than grind through the queue and amplify the response. A 429 on a row's lookup is different: it costs that row one attempt, and the loop continues.

LWW is strict: >, not >=

On a timestamp tie, the local copy stays. A tied remote record is normally the version this device already holds. One exception: a backfill sync accepts a tie, so a newly synced field reaches rows an older build stored without it. A separate ceiling guards against bad clocks. A remote stamp more than 5 minutes ahead of now (MAX_CLIENT_CLOCK_SKEW_MS) is clamped on pull, never counts as newer on push, and never overwrites a row with a pending queued write. The pull cursor is the lenient side: it queries with >= and a 30-second overlap.

Device-local fields are not synced through

The device-local fields are notificationSent, lastNotificationAt, and snoozedUntil. They are kept from the existing local row when a remote update lands, and a pull that moves the due date resets them. parentTaskId is a separate case: it has no wire field, so it always comes from the local row. Adding a new device-local field means editing localReminderState or pocketBaseToTaskRecord in task-mapper.ts, not just the schema.

Echo filter needs both sides non-empty

A bare equality check would treat two empty device ids as “this is my echo, skip it” and drop legitimate events. The actual check requires both ids to be non-empty and equal.

How deletes travel

A local delete is pushed as its own queue op. Separately, pull ends with reconcileDeletedTasks(). The function fetches the remote index, the list of task ids the account holds. It removes any local task that list no longer names, unless a pending queue row protects the task. A task with no pending row and at least one retry-exhausted row moves to Trash and is not dropped outright. A realtime delete event follows the same rule. Before the function deletes anything, it confirms the session with the server. If the remote index fetch fails, reconciliation is skipped. A stale row is better than deleting real data from an incomplete view.

Raw error messages from PB must never be persisted

4xx responses can echo task content (titles, descriptions) back. Push errors run through sanitizeSyncError() to a stable code before they reach a queue row's lastError or the sync history. Do the same if you add new write paths.

Local dev tip

OAuth sign-in against production PocketBase completes only on gsd.vinny.dev, because the hosted bounce returns there. To test sign-in locally, run PocketBase at 127.0.0.1:8090 with --hooksDir=docker/pb_hooks and GSD_WEB_OAUTH_CALLBACK_URL=http://localhost:3000/auth/callback/. It needs its own provider setup, with the right redirect URIs registered. That hooks folder also loads the task encryption hooks, so task writes fail unless GSD_TASKS_ENC_KEY holds a 32-character key.

08

If you only remember four things

TL;DR

  1. Local Dexie is the source of truth. PocketBase is a fan-out mirror.
  2. Remote queries filter and sort timestamps on client_updated_at. System fields are off-limits.
  3. Mutations enqueue durably. The background sync manager and the coordinator decide when to flush.
  4. Realtime SSE and pull follow the same LWW rule: a strictly newer remote wins.
01 / Source of truth

Treat Dexie as the database. PocketBase is replication infrastructure.

02 / Custom timestamps

Always client_updated_at. The updated system field is off-limits for filter/sort.

03 / Durable queue

Mutations enqueue locally. The background sync manager schedules, and the coordinator runs one sync at a time.

04 / One merge rule

Pull and realtime both let a strictly newer remote win. Only a backfill sync accepts a tie.
