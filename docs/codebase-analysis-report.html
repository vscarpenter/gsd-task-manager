07 · Methodology and limitations

Evidence boundaries

This was a read-only engineering audit of the current working tree. The only intentional repository write is this canonical report.

Method

  • Read the supplied audit worklist, current dirty coding-standards.md, project guidance, security boundary map, security policy, and subsystem rules.
  • Fetched the current Inkwell agent instructions successfully and applied the system directly; no local fallback was used.
  • Ran the exact root coverage and three-browser Playwright collection commands after installing Chromium, Firefox, and WebKit.
  • Ran MCP coverage, PocketBase system tests, lint, typecheck, shape ratchet, Bun audit, dependency freshness, license inventory, and full-history Gitleaks.
  • Inspected production source, tests, configuration, nine workflows, deployment scripts, Docker/Caddy/CloudFront configuration, PocketBase hooks/migrations, and documentation.
  • Excluded generated output, vendor directories, lockfiles, and build artifacts from static findings.

Limitations

  • One E2E run is one data point. No historical CI artifact was available, so this report does not claim duration or flake trends.
  • The focused 9/9 Chromium repeat localizes likely flakiness but does not prove the root cause.
  • The live PocketBase test used disposable local instances at 0.39.10 and 0.26.6; the production endpoint was not probed by this audit. Its 0.39.10 version is user-verified.
  • OAuth providers, production CloudFront/Caddy headers, Sentry ingestion, deployment credentials, and remote data were not exercised.
  • No production build was run because the audit’s anti-goal permits only the report write and the build updates tracked generated metadata. Build fail-closed behavior was source- and unit-test-verified.
  • License observations are an engineering inventory, not legal advice.
  • Pre-existing working-tree changes in coding-standards.md and public/sw.js were preserved and treated as current audit input.
